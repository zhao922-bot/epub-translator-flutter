# 续传缓存恢复阶段设计

## 背景

翻译失败后点击“继续翻译”时，控制器会先把任务的 `progress`、`completedBlocks`、`cachedBlocks` 和 `resumedBlocks` 全部重置为零。仓库层随后才逐章查询块缓存，并且缓存查询与新的 API 翻译交错执行。实际缓存仍然存在，但界面会先显示“0% 翻译中”，导致用户合理地认为断点已经丢失。

现有实现还有一个数据安全问题：仓库加载旧断点后，会在完成缓存校验前用零进度保存新的 `running` 状态。若应用在缓存扫描期间退出，原有断点数字可能被零进度覆盖。

## 目标

为失败或取消任务的续传新增独立的“恢复缓存”阶段：

1. 点击“继续翻译”后，立即把历史断点作为“待校验进度”显示，例如 `605/1643（37%）`。
2. 在任何翻译、脚注合批或书籍记忆 API 请求之前，扫描并校验本次配置可用的全部块缓存。
3. 缓存扫描期间显示独立的扫描进度和已确认缓存数量。
4. 扫描完成后，以实际命中数量替换待校验数字，再进入“继续翻译”阶段。
5. 明确记录缓存恢复阶段未调用 API；若全书均命中缓存，则明确记录整个任务未调用 API。
6. 缓存恢复期间不得把持久化断点回退为零。

## 非目标

- 不改变缓存键组成、翻译质量校验、脚注合批或书籍记忆的内容逻辑。
- 不为缓存建立新的数据库或完整索引文件。
- 不保证配置改变后继续显示旧任务的 37% 为有效进度；旧数字只作为待校验提示，最终以当前配置的实际缓存命中为准。
- 不在本次修改中调整网络重试次数或退避算法。

## 方案

采用完整预扫描方案：仓库在翻译入口计算当前 `jobKey`，加载兼容断点，然后遍历所有已选择块并读取块缓存。预扫描返回一个内存中的缓存结果集合，后续正文和跨文件脚注流程直接消费该集合，不再重复读取磁盘。

这种方案在发出第一个 API 请求前即可确定真实的可复用数量，也能从结构上保证“恢复缓存”阶段没有 API 调用。对于当前典型的数千个块，内存保存已翻译 HTML 的成本可控，且避免了第二次磁盘扫描。

## 状态模型

### 任务阶段

`TranslationJobPhase` 增加 `cacheRestoration`，完整阶段顺序为：

```text
inspection → cacheRestoration → translation → completed/failed/cancelled
```

新增阶段只表示本地磁盘工作，不表示 API 翻译已经开始。

### 恢复字段

`TranslationJob` 增加以下可序列化字段，旧历史记录缺失字段时按零处理：

- `resumeCheckpointBlocks`：历史任务声称已经完成、等待校验的块数。
- `cacheScanScannedBlocks`：本次已经检查缓存的块数。
- `cacheScanTotalBlocks`：本次需要检查缓存的块总数。

现有字段含义保持不变：

- `completedBlocks`：在恢复阶段开始时显示历史待校验值；预扫描结束后改为实际缓存命中数；翻译阶段继续累计新翻译块。
- `cachedBlocks`：本次预扫描实际命中的缓存块数。
- `resumedBlocks`：存在兼容断点时，本次预扫描实际命中的缓存块数；普通重复运行但没有断点时仍可记录 `cachedBlocks`，不记录为断点续传。

### 控制器中的续传提示

`retryJob` 从失败或取消的历史任务建立一次性 `ResumeProgressHint`，包含原任务的 `completedBlocks` 与 `totalBlocks`。检查书籍与恢复风格档案期间保留该提示。创建排队任务时用提示值显示待校验进度，不再无条件归零。

该提示不是缓存有效性的证明。仓库计算当前 `jobKey` 后：

- 找到兼容 `JobResumeState`：进入恢复阶段，并使用持久化断点作为权威待校验值。
- 未找到兼容状态：清除提示，记录配置或缓存不兼容，并从零开始完整缓存扫描。

## 数据流

1. 用户对失败或取消任务点击“继续翻译”。
2. 控制器保存 `ResumeProgressHint(605, 1643)`，重新检查 EPUB，并保留已确认的风格档案。
3. `startTranslation` 创建 `cacheRestoration` 排队任务，界面立即显示“正在恢复缓存 · 待校验 605/1643（37%）”。
4. 仓库计算输入、配置、章节和风格档案对应的 `jobKey`，加载兼容断点。
5. `CacheRestorationScanner` 遍历全部已选块：
   - 计算与现有逻辑完全一致的块缓存键；
   - 读取非空缓存内容；
   - 按章节路径和块 ID 保存命中内容；
   - 节流发送扫描进度，避免每个块都重建界面。
6. 扫描期间只允许文件读取、取消检查和进度回调，不允许持有或调用 API 客户端。
7. 扫描完成后发送一次确定结果，例如“已扫描 1643/1643，确认复用 605 块”。
8. 仓库把实际命中数写入断点，然后切换到 `translation` 阶段。
9. 正文与脚注翻译流程直接读取预扫描结果；仅对未命中的块调用 API。
10. 若全部块命中，跳过翻译和书籍记忆请求，直接重打包 EPUB。

## UI 与文案

进度卡在恢复阶段显示：

```text
正在恢复缓存
待校验断点：605/1643（37%）
缓存扫描：820/1643
已确认复用：354 块
```

扫描结束且仍有未翻译内容时切换为：

```text
继续翻译
已复用 605 块，将从剩余 1038 块继续
```

日志使用以下语义：

- 开始：`发现断点 605/1643，正在校验本地缓存。`
- 扫描完成：`已复用 605 块；缓存恢复阶段未产生 API 请求。`
- 缓存不足：`断点记录为 605 块，实际可复用 598 块；7 块缓存缺失或不可读，将重新翻译。`
- 全部命中：`已复用全部 1643 块，本次未产生 API 请求。`
- 无兼容断点：`当前模型、翻译设置或书籍选择与原任务不兼容，旧断点仅供提示，本次未命中兼容断点。`

中英文文案都通过 `AppStrings` 提供，不在组件中硬编码。

## 持久化与失败处理

- 加载兼容断点后，不立即用零进度覆盖它。
- 扫描完成前发生取消或应用退出时，保留上一次已完成断点；下一次仍可重新校验。
- 扫描完成后，保存实际命中数及 `cacheRestoration`/`running` 状态。
- 单个缓存文件不存在、为空或不可读时按缓存未命中处理，并累计缺失数；不能让整本书恢复失败。
- 无法读取任务状态文件时按无兼容断点处理，但仍完整扫描块缓存，因为块缓存可能仍然可用。
- EPUB、模型、目标语言、术语表、质量检查或风格档案导致缓存键改变时，旧缓存自然不命中，不复用不兼容内容。
- 用户取消缓存扫描时不得发出 API 请求，任务保存为 `cancelled`。

## 组件边界

### `CacheRestorationScanner`

职责仅限计算/读取块缓存并产生 `CacheRestorationResult`。它依赖缓存存储、缓存键生成函数和取消检查，不依赖 `Dio`、翻译客户端或提示词构建器。

### `CacheRestorationResult`

包含按章节路径和块 ID 索引的翻译 HTML、扫描总数、命中数、缺失/不可读数以及是否来自兼容断点。正文和脚注流程只读取结果，不自行重复查盘。

### 控制器

负责历史断点提示、阶段切换后的展示状态以及日志汇总，不判断缓存是否有效。

### 仓库/章节翻译器

负责确定兼容 `jobKey`、调用预扫描器、在扫描完成后启动现有翻译流程，并保证 API 调用顺序。

## 测试策略

遵循测试驱动开发，先增加会在现有实现上失败的测试：

1. 控制器测试：重试 605/1643 的失败任务后，排队/恢复状态立即保留 605 和 37%，而不是归零。
2. 控制器测试：恢复阶段显示独立扫描字段，收到实际命中结果后再切换到翻译阶段。
3. 仓库测试：预置部分块缓存时，必须扫描完全部块后才允许第一次 API 调用。
4. 仓库测试：扫描过程中取消时 API 调用次数为零，旧断点不被零进度覆盖。
5. 仓库测试：缓存文件缺失、为空或不可读时按未命中处理，扫描继续完成。
6. 仓库测试：全部块命中时翻译和书籍记忆 API 调用次数均为零，并能完成 EPUB 重打包。
7. 仓库测试：部分命中时仅未命中块请求 API，预扫描命中内容同时适用于正文块和跨文件脚注块。
8. 序列化测试：旧 `TranslationJob` JSON 缺少新增恢复字段时仍能正常加载。
9. 组件测试：进度卡在 `cacheRestoration` 阶段显示待校验、扫描和确认复用三种数字；进入 `translation` 后显示“继续翻译”。

完成定向测试后运行完整 `flutter test`、`flutter analyze lib test`，并在没有活动翻译任务时构建 Windows Release。

## 验收标准

- 对保存为 605/1643 的失败任务点击继续后，首个恢复界面显示 605/1643 和 37%，不显示 0%。
- 缓存扫描过程能观察到扫描计数增长，阶段名称始终为“正在恢复缓存”。
- 在扫描完成事件之前，测试记录的所有 API 调用计数为零。
- 扫描完成后显示实际复用数量；若缓存完整则为 605，随后只翻译剩余块。
- 日志明确区分“缓存恢复阶段零 API 请求”和“全任务零 API 请求”。
- 缓存缺失时不会虚报复用数量，也不会因单个损坏缓存中止整本书。
- 取消或意外退出缓存扫描不会把旧断点覆盖为零。
- 现有正常首次翻译、整书缓存命中、脚注合批、风格档案和任务历史恢复测试均保持通过。
