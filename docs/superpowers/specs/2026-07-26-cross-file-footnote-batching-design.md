# 跨文件脚注合批翻译设计

## 背景

部分 EPUB 将每一条脚注保存为独立 XHTML 文件。`Communion` 的 72 个待译文件中，末尾包含连续脚注文件；每个文件通常只有一个 `p-1` 块。当前调度器只在单个章节内部合批，因此每条脚注都会触发一次 API 请求。

真实验收中，缓存命中 1,631 个块后，剩余 12 条脚注仍需要逐条请求，明显放大了网络往返时间与重复系统提示词的 Token 消耗。

## 目标

- 保留并翻译所有已选脚注，不跳过任何脚注文件。
- 将连续的独立脚注文件合并为受大小限制的 API 微批次。
- 继续按原 XHTML 文件和原块 ID 回写，保持脚注链接、锚点与阅读器定位不变。
- 逐块复用、写入和验证缓存，确保中断后续传不会重复翻译已成功脚注。
- 保持主章节的段落上下文、书籍记忆和既有批处理逻辑不变。

## 非目标

- 不增加“跳过脚注”选项。
- 不把正文段落与脚注混合到同一批次。
- 不改变 API、模型、风格档案、术语表或块缓存键的含义。
- 不通过拆改原文规避服务商内容审核。
- 不在本次实现中增加新的设置页控件。

## 候选识别

仅将满足以下全部条件的已选章节视为“独立脚注章节”：

1. 路径文件名匹配 `-fn.xhtml`、`-fn.html`、`footnote` 或 `endnote` 的常见变体；
2. 标题、EPUB 语义或文档路径能够确认其为脚注/尾注；
3. 章节包含至少 1 个可翻译块；
4. 该章节与下一候选章节在翻译顺序中连续。

识别不确定时，章节继续走现有单章节翻译路径，不进行跨文件合批。主章节、目录、版权页、索引、广告页和普通附录不会被混入脚注批次。

## 数据模型与请求映射

现有 `ExtractedBlock.id` 在不同文件中可能重复，例如多个脚注文件都使用 `p-1`。因此跨文件请求不能直接以块 ID 作为全局键。

新增不可变的 `FootnoteBlockRef`：

```text
requestId       本次请求唯一 ID，例如 f17:p-1
chapterIndex    在已选章节中的顺序
chapterPath     原 XHTML 路径
chapterTitle    用于日志
block           原 ExtractedBlock
cacheKey        该块现有缓存键
```

API 载荷的 `blocks[].id` 使用 `requestId`。收到响应后，必须严格校验：

- 响应数量与请求数量一致；
- 每一个 `requestId` 恰好出现一次；
- 每条 HTML 均通过既有标签锁定、空译文和源语言残留检查；
- 验证后的译文只写回对应 `chapterPath + block.id`。

模型不会需要或看到用户本地绝对路径；`requestId` 只表示批次内的技术标识。

## 调度与合批

翻译主循环在遇到独立脚注章节的连续区间时，执行以下流程：

1. 扫描该连续区间，逐块读取既有缓存。
2. 缓存命中立即归入其原章节，计入进度和续传统计；未命中块生成 `FootnoteBlockRef`。
3. 使用现有 `chunkSize` 作为字符预算，并额外限制每批最多 12 条脚注。达到任一上限时结束当前微批。
4. 每个微批保留已确认风格档案、术语表和书籍记忆，但不附加相邻正文段落上下文，避免把无关正文带入引文翻译。
5. 按 `maxConcurrent` 窗口发送微批。一个请求返回后，逐块校验、缓存和归档到原章节状态。
6. 当连续区间内的所有章节都已获得缓存或有效译文后，再按原顺序标记文件完成、更新预览和写入 EPUB。

正文章节仍沿用既有“章节内批处理 + 相邻上下文 + 章节记忆更新”流程。脚注区间不会改变正文前后的章节顺序，也不会让书籍记忆把脚注误当作正文摘要来源。

## 错误与中断策略

- 网络、限流、超时和服务端暂时错误继续使用现有退避重试策略。
- 若跨文件批次因 `413`、批次 JSON 格式不匹配或可安全降级的批次错误无法完成，则按现有块级翻译逻辑处理该微批中的各条脚注；成功条目照常写入缓存。
- 认证错误、模型不存在和其他全局错误继续中断任务，不静默跳过脚注。
- 每成功写入一条脚注，都更新相应块缓存和恢复清单。中断后只请求仍未命中的脚注。
- 现有块缓存键保持不变，因此本设计发布后可以复用旧版本已完成的 1,631 个缓存块。

## 日志与进度

日志以不泄露正文的摘要形式显示：

```text
Prepared 2 cross-file footnote batches for 11 blocks across 11 files.
Performance: footnote batch 1/2 (6 blocks) took 8 sec.
Completed footnote file 4/11: Footnote.
```

进度仍以块数和文件数为准。用户可以看到所有脚注都被纳入总数，但不需要理解内部请求合并细节。

## 测试范围

### 单元测试

- 连续 `-fn.xhtml` 文件按字符预算与 12 条上限合并。
- 非连续脚注、普通正文和无法确认类型的文件不会跨文件合批。
- 不同章节的 `p-1` 生成不同 `requestId`。
- 混合缓存命中与未命中时，仅未命中脚注进入 API 批次。
- 响应缺失、重复或未知 `requestId` 必须失败，不能错写到其他文件。
- 每条返回译文继续执行 HTML 结构和残留语言校验。
- 批次降级后成功脚注仍保留，失败原因保持现有语义。

### 仓库与控制器测试

- 脚注区间完成后，原章节顺序、完成文件数和完成块数正确。
- 取消后续传只请求未缓存脚注。
- 旧缓存键在新逻辑下仍然命中。

### 真实 EPUB 验收

- 使用 `Communion` 的末尾连续脚注文件。
- 记录旧逻辑的请求数与新逻辑的请求数。
- 验证脚注中的 `href`、`id`、`epub:type` 和每个 XHTML 文件仍保留。
- 验证译后 EPUB 可重新检查，块数与选中源文件一致。

## 验收标准

- 连续 12 条单块脚注最多使用 2 个 API 请求（受字符预算影响时允许更多）。
- 所有脚注仍会出现在译后 EPUB 中，并保留各自的锚点与返回链接。
- 不同脚注文件中同名 `p-1` 不会发生译文串写。
- 中断后续传时，已完成脚注不重复调用 API。
- 主章节翻译、风格档案注入和既有缓存命中行为不回归。
